### On the brief's questions
- **The two "carrying the exception once" tests.** They are honest evidence for the bullet. The bullet describes behavior, and the tests assert it at `[integration]`: the root test checks one inner exception and then a clean second `WaitForTasks()` (so the exception surfaces once), and the child test checks one inner exception from the root. They passed before the change because, before it, only the write was registered. This plan registers the `RunRules(propertyName)` run as well, and that is what creates the duplicate the bullet rules out, so passing before the change does not make them vacuous. What has no recorded red run is the map's claim that they fail without the de-duplication (see Could not verify). If the orchestrator wants that claim backed the way WAIT-003's guards were, one run with the `ReferenceEquals` filter disabled would show it.
- **`SaveWithAToken_OnARoot_...`** It pins the Acceptance bullet exactly, and the Punchlist row's done-when ("a test saves a root with a token after a child write"). It is also a real measure of the ordering, not a side effect: `004-red.log` shows it failing with `SaveOperationException` (busy) under the old parent-first order. It pins one consequence of "an object accounts before its parent", for one hop through a child property. It does not pin the general statement. That statement is in the plan's Intent, not in an Acceptance bullet, so this is not a finding.
- **Bullet wording that claims more than its test shows.** Two bullets claim a little more than their tests show: the `[unit]` bullet ("The generated setter", which covers three templates, two tested) and the lazy-load bullet ("on the parent", where only an `EntityBase` parent is tested). Both are listed as callouts above. The other bullets match their tests.

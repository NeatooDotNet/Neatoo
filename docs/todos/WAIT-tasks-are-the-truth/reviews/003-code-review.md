The deliverable landed as scoped and in the right layer. The busy bool, the id list and the mark/unmark members are gone (`src/Neatoo/IValidateProperty.cs`, `src/Neatoo/Internal/ValidateProperty.cs`). Each property takes a tracker from `IFactory.CreateAsyncTasks()` at the one `Attach` seam the three entry paths share (`ValidatePropertyManager.cs:94-103`, called from `:167`, `:255`, `:283`). `ValidateBase.TryGetProperty` creates a property on first use through `GetProperty`, so a rule's trigger property always has a tracker by the time `RuleManager.RunRule` hands it the run. Busy and the property's wait both read the tracker (`ValidateProperty.cs:73`, `:79-83`). The rule manager hands over a task where it used to hand over an id, and that task covers the message application, as Step 4 asks (`RuleManager.cs:706-735`). The DI change is correct: `CreateValidatePropertyManager` and `CreateEntityPropertyManager` resolve `IFactory` from the provider that resolved them (`AddNeatooServices.cs:91`, `:99`), so the transient `DefaultFactory` gets the caller's `CreateAsyncTasks`. Nothing singleton depends on `IFactory`. The parameterless `DefaultFactory` falls back to `new AsyncTasks()` only on the non-DI constructors, the same as WAIT-002's `asyncTasksFactory` default, so it fits D36. The two lazy-load classes re-declare `IValidateProperty`/`IEntityProperty`, so their `new` members are what the interface dispatches to, and they now add `HasTasksInFlight` and `WaitForOwnTasks()`. That is the smallest change that keeps their documented waiting, and it builds nothing new on LazyLoad. For where the arc is going, `TrackTask` is the right seam for D32 ("a property reports each task it starts tracking to its entity"): WAIT-004 can register at that one point. `ValidatePropertyManager.WaitForTasks` is transitional under D33 and suspends correctly: every wait it awaits is incomplete, and it terminates once a scan finds none. I traced the overlap, fault and re-entrancy cases in `TrackTask` and found no deadlock. `accounted` is the unwrapped `SequenceCompleted` (`AsyncTasks.cs:85-88`). It completes when this task's accounting is done and never waits on `AllDone`. So a rule run and a write cascade tracked on the same property do not wait on each other. Work started from the idle callback joins the open sequence (`AsyncTasks.cs:75-77`, `:233-237`). The one thing I could not accept is where an exception thrown by the property's completion callback ends up (veto-tier below).

### Veto-tier
- **`src/Neatoo/Internal/ValidateProperty.cs:117-121`, with `AsyncTasks.cs:214-226` and `:241-252` · Medium (read and traced, not run).** It contradicts the DESIGN DECISION at `src/Neatoo/ValidateBase.cs:365-366`, "a synchronous fault surfaces the way a setter's does", and the plan's own invariant at `plans/003-property-tasks.md:33`, "A property's tracker reports no fault". The property's idle notification now runs inside the tracker's `OnFullSequenceComplete`. When a property goes idle on a path the entity does not register (`IValidateProperty.SetValue`, which every MudNeatoo input uses, and `RunRules(propertyName)`), that notification is what flips the entity's `IsBusy` to false: `RunningTasks.IsRunning` is false and the manager's cached `IsBusy` falls. So it runs `CheckIfMetaPropertiesChanged` and then any sync rule triggered on `IsBusy` (`ValidateBase.cs:388-406`). If that rule throws, or any `PropertyChanged` subscriber on the property or the entity throws, nothing on the path catches the exception (`ValidateProperty.OnPropertyChanged`, `ValidatePropertyManager.Property_PropertyChanged`, `ValidateBase._PropertyManager_PropertyChanged`). `SequenceCompleted` does catch it and puts it into the property's `AllDone`. `accounted` does not carry it, so the awaited `SetValue` / `RunRules` now completes cleanly. Before this plan the same throw escaped the inline `OnPropertyChanged(nameof(IsBusy))` in `OnValueNeatooPropertyChanged` / `RemoveMarkedBusy` and faulted the awaited write or run. Where the exception goes now:
  - If an entity `WaitForTasks()` is scanning the property at that moment, it throws the exception.
  - If nothing is waiting, the exception is kept as `_unobservedFault`. The next manager scan is handed it and drops it, because the faulted wait is already complete (`ValidatePropertyManager.cs:78`): it surfaces zero times.
  - Or the property's next write starts a sequence that carries it (`AsyncTasks.cs:64-67`), and it surfaces later from a wait on unrelated work.

  What must change: an exception raised by the property's completion callback has to reach the operation whose accounting raised it, as it did before, or the documented rule has to be ruled on again. One option: let `accounted` (or the caller that awaits it) carry callback exceptions. Another: raise the idle notification from the accounting caller rather than from inside the tracker. Reachability depends on the arc's later plans. WAIT-004 (registration) and WAIT-005 (busy read from the entity's tracker) move most `IsBusy` flips back to the entity's callback, whose faults WAIT-002 already reports. A property-level `PropertyChanged` subscriber that throws stays on this path either way.

### Callouts
- **`src/Neatoo/Internal/ValidatePropertyManager.cs:76-79` · Medium · `Affects: AC-7` · `Reachable by:` a child entity's async rule throws after a generated-setter write; the parent's first `WaitForTasks()` throws it (the parent's copy, via `AddChildTask`); the parent's second `WaitForTasks()` reaches the child property.** The scan now calls `WaitForTasks()` on every property, where the old loop called it only on properties reporting `IsBusy`, and it skips waits that are already complete. A property holding a child calls `child.WaitForTasks()`, and the child's `RunningTasks.AllDone` hands over its held fault (`AsyncTasks.cs:116-121`). The wait faults synchronously, is filtered out as complete, and is never awaited. Three consequences: the parent's wait drops the child's fault without a word; a later `child.WaitForTasks()` no longer reports it, which it did before this plan; and the dropped faulted task raises `TaskScheduler.UnobservedTaskException` when it is finalized. Whether this scan surfaces a fault depends on whether the wait was already complete when the scan took it. The doc comment at `ValidateProperty.cs:75-78` ("It never faults: a rule's exception surfaces from the entity's wait") is false for a property holding a child, and false given the veto finding above. One option: filter only on `IsCompletedSuccessfully`, so that a faulted wait is awaited.

### Direction & shape
The change goes where it should. There is one internal helper, `src/Neatoo/Internal/NeatooPropertyChangedInvocation.cs` (`InvokeAll`), and every place the framework raises `NeatooPropertyChanged` now calls it: `ValidateProperty.PassThruValueNeatooPropertyChanged` and `OnValueNeatooPropertyChanged` (`Internal/ValidateProperty.cs:412`, `:422`), `ValidatePropertyManager._Property_NeatooPropertyChanged` (`:139`), `ValidateBase.RaiseNeatooPropertyChanged` (`:445`) and `ValidateListBase.RaiseNeatooPropertyChanged` (`:331`). I grepped `src/Neatoo`, `src/Neatoo.BaseGenerator` and `src/Neatoo.Blazor.MudNeatoo` for `NeatooPropertyChanged`, `?.Invoke(`, `delegate Task`, `Func<…Task>` and `event`. No other invocation of the delegate exists. The generator emits none. The lazy-load properties (`LazyLoadValidateProperty.cs:321`, `LazyLoadEntityProperty.cs:237`) and `LazyLoadPropertyHelper.ConnectInnerChild` raise through the base `OnValueNeatooPropertyChanged` and `PassThruValueNeatooPropertyChanged`, so they are covered. `EntityBase.ChildNeatooPropertyChanged` (`EntityBase.cs:448`) only forwards to the base. `EntityListBase` has no override. The framework's other task-returning delegates have a single target by construction: `IAsyncTasks.OnFullSequenceComplete` is a property assigned with `=` (`ValidateProperty.cs:123`, `ValidateBase.cs:219`), and `TaskStarted` and `_reportToOwner` are `Action<Task>`. RemoteFactory's `LazyLoad<T>` raises only `PropertyChanged`.

`InvokeAll` meets the plan's constraints:
- Subscribers are called in subscription order, on the caller's thread.
- With a single target it returns that subscriber's task directly: no list, no `WhenAll`.
- A synchronous throw still propagates out of the loop and stops later subscribers. `OnValueNeatooPropertyChanged` captures it into its task, and `SetValue` rethrows it.
- When a rule and a consumer both fault, the rule's fault is the one reported. The manager subscribes to its property at `Register`, before any consumer can, so its task is first in the `WhenAll` array, and `await` reports the first faulted task in array order. That keeps WAIT-003's rule "a rule's own exception is reported over a listener's".

The three AC-10 tests drive the natural paths: a write through `SetValue`, and a consumer on the object and on the property. Each failed red for the stated reason. I did not re-walk the test review.

**Reflection.** I agree with your reading. `Delegate.EnumerateInvocationList<TDelegate>` and `Delegate.HasSingleTarget` are in `System`, not `System.Reflection`. They look up no metadata and produce no `MethodInfo`. Each subscriber is called as a typed `NeatooPropertyChanged`, so nothing is invoked late-bound. Neither API touches `Delegate.Method` or `DynamicInvoke`. Both exist on net9.0 and net10.0, the only targets (`Directory.Build.props:9`).

**Deadlocks.** Not as a new class; one ordering-dependent escape is gone. I traced it as follows.
1. A write's task is the whole cascade: property, manager, `ChildNeatooPropertyChanged`, rules, then the object's own `RaiseNeatooPropertyChanged`.
2. `SetValue` reports that task to the owner after the cascade first suspends (`ValidateProperty.cs:261`). `AddChildTask` then registers it with the object and its parents.
3. With an async rule on the property, the object's subscribers run after `await this.RunRules(...)` resumes (`ValidateBase.cs:463-465`). By then the write is in `RunningTasks`.
4. A subscriber that then awaits `WaitForTasks()` on that object or an ancestor is waiting for a task that contains itself. Before this plan, that deadlocked whenever the subscriber was the only or the last subscriber. It escaped only when another subscriber came after it, because its task was then dropped. That escape was the D6 bug.

The parent case is the same. The parent's property subscribes to the child first, so a parent handler that awaits the child's or its own wait already deadlocked whenever nobody else subscribed to the child. It escapes now only where a later consumer used to make the framework drop the parent's cascade. The same applies to `RunRules(RunRulesFlag)`, which awaits `RunningTasks.AllDone` (`ValidateBase.cs:989`), and to `Save(token)`. Without an async rule and without an await before the wait, the subscriber's synchronous call finds no registered work and does not suspend. No live subscriber in the repo awaits a wait: `NeatooValidationSummary.OnNeatooPropertyChanged` returns `Task.CompletedTask`, and `WorkOrderTaskList.HandleNeatooPropertyChanged` calls the sibling's `RunRules(string)`, which does not await `AllDone`. Listed below as a callout because the deadlock is now reachable by subscription order alone.

**AC-12 parking claim: it holds.** `EntityBase.Save()` awaits `Factory.Save((T)this)` (`EntityBase.cs:502`). `IsBusy` is `RunningTasks.IsRunning` (`ValidateBase.cs:172`). The generated local save (`OrderFactory.g.cs`, `LocalInsertCore` `:191-218`, `LocalUpdateCore` `:262-289`) awaits the `[Insert]`/`[Update]` and then calls `FactoryComplete(Insert|Update)` on the same instance, inside the save's own task. `EntityBase.FactoryComplete` (`:612-615`) calls `MarkUnmodified`, which throws `InvalidOperationException` while `IsBusy` (`:306-313`) and does not check pause. If the save's task were registered in `RunningTasks`, it would still be running at that point for any async operation, so every such local save would throw. A synchronous operation that completes the save synchronously would not register and would not throw, which matches the plan's "async `[Insert]` or `[Update]`". I traced this; I did not run it.

### Callouts
- `src/Neatoo/Internal/NeatooPropertyChangedInvocation.cs:24-37` · High · `Affects: AC-10` · `Reachable by:` a consumer subscriber that returns `null` instead of a task (a project with nullable off, or nullable warnings ignored). The old raise was `NeatooPropertyChanged?.Invoke(args) ?? Task.CompletedTask`, so the `??` also absorbed a `null` from the last (or only) subscriber. Now the single-target path returns that `null`, and `await` in `ChildNeatooPropertyChanged` or `OnValueNeatooPropertyChanged` throws `NullReferenceException`. The multi-target path hands `null` to `Task.WhenAll`, which throws `ArgumentException`. Either way the write faults and the setter rethrows it. Under the old code that handler was harmless. No subscriber in the repo returns `null`. One option: treat a `null` task as completed in both paths.
- `NeatooPropertyChangedInvocation.cs:31-36`, with `ValidateBase.cs:463-465` · Medium (traced, not run) · `Affects: AC-10` (and AC-9 for WAIT-008's prose) · `Reachable by:` a consumer handler on an object's `NeatooPropertyChanged` that awaits `WaitForTasks()`, `RunRules()` or `Save(token)` on that object or an ancestor, when the property has an async rule and another subscriber comes after the handler. That ordering deadlocked under neither version before this plan and deadlocks now. Without the later subscriber it already deadlocked. See Direction & shape. This is the intent working ("whichever order the handlers subscribed in"), but nothing in the guides tells a handler author it must not wait on its own graph. `docs/guides/blazor.md:102` says "Before reading validity in code — a test, a handler — `await entity.WaitForTasks()`", which a reader could take to include a `NeatooPropertyChanged` handler. One option: state the rule in WAIT-008's docs.

# Neatoo 0.32.0

**Release date:** TBD
**Breaking changes:** Yes — see [Migration](#migration).

## Summary

Fixes four defects in `EntityListBase` / `ValidateListBase` state machinery. Two are user-visible
and one of those changes save behavior for existing consumers.

The headline fix: after a save that carried child deletions, editing a child again now makes the
aggregate savable. Previously the list's `IsModified` value silently self-healed but raised no
notification, so parents and bindings never learned there was unsaved work, and the aggregate kept
reporting not-savable while holding real user edits.

## What's new

### Fixed — a save carrying deletions swallowed the next edit's notification

`EntityListBase.FactoryComplete(Update)` resumed before clearing `DeletedList`, and the resume
snapshotted the meta-state baseline while the deletions were still queued — recording
`IsModified = true`. Clearing `DeletedList` then made the real value `false` with nothing to
correct the baseline. The list sat at actual-`false` / baseline-`true`, so the user's next child
edit compared true-against-true and announced nothing.

Only reachable on a **local / fat-client save**: a `[Remote]` save deserializes the returned graph,
and `OnDeserialized` rebuilt a correct baseline, which is why the defect was invisible to the whole
test suite.

### Fixed — `Delete()` inside a paused window silently dropped a child

`EntityBase.Delete()` delegated unconditionally to `ContainingList.Remove(this)`, and
`RemoveItem`'s paused branch neither marks the item deleted nor queues it. A delete issued inside a
factory operation removed the child and recorded nothing, so no DELETE was ever issued.
`Delete()` now records the deletion in place when its containing list is paused, and routes through
the list exactly as before when it is live.

### Fixed — replacing a list element silently orphaned the displaced row (**breaking**)

`list[i] = replacement` performed cache arithmetic only. The displaced item was dropped with no
`MarkDeleted` and no `DeletedList` entry, so replacing a **persisted** child orphaned its row — the
save issued an INSERT or UPDATE for the replacement and nothing at all for what it displaced. The
incoming item also received no `IsChild` or `ContainingList`, and none of `Add`'s guards ran.

`SetItem` now behaves like the remove-plus-insert it reads as:

- the displaced item is marked deleted and queued for persistence deletion when it was persisted,
  and discarded when it was new (matching `RemoveItem`);
- the incoming item receives child identity on both the live and paused branches (matching
  `InsertItem`);
- the live branch enforces the same duplicate, busy, and aggregate-boundary guards as `Add`;
- an `IsModified` transition caused by a replacement is announced.

Replacing an item with itself remains a no-op. The paused branch queues nothing — factory and
deserialization input is trusted, consistent with `InsertItem`.

### Also

- `EntityListBase.IsModified` transitions raise `PropertyChanged`. A standing note in the test
  suite claimed they did not; that claim was disproven and removed.
- The `ResumeAllActions` pause guard is documented: `FactoryComplete` on a never-paused **list** is
  a correct no-op, because lists expose no `PauseAllActions()` and generated factories always pair
  `FactoryStart` with `FactoryComplete`.

## Migration

Two behavior changes can affect existing code. Both are cases where the old behavior lost data
silently.

**1. Replacing a persisted child now DELETEs its row.**

```csharp
order.Lines[0] = replacement;   // displaced line's row survived in 0.31.0
await order.Save();             // 0.32.0: the displaced line is DELETEd
```

If you relied on replacement as an identity-preserving swap — substituting a refreshed instance for
a stale one representing the same row — that row will now be deleted. Re-fetch the list instead:

```csharp
order = (IOrder)await orderFactory.Fetch(order.Id);
```

**2. Replacing an element now enforces `Add`'s guards.** A replacement that duplicates an item
already in the list, uses a busy item, or crosses an aggregate boundary throws
`InvalidOperationException` where it previously succeeded silently. These were always violations;
`SetItem` simply did not check.

**3. A list may now report `IsModified == true` where it previously reported `false`** — after a
replacement, because there is a pending deletion to save. This is the corrected answer: a list with
a queued DELETE has unsaved work.

# Neatoo 0.37.0

**Release date:** 2026-11-24
**Breaking changes:** Yes — see [Migration](#migration).

## Summary

Neatoo now keeps one record of async work: tasks. Every write and every rule run is a task in its
object's running tasks, whoever started it. `WaitForTasks()` awaits those tasks, and `IsBusy` reads
them.

This fixes the freeze in [#141](https://github.com/NeatooDotNet/Neatoo/issues/141), where
`WaitForTasks()` looped without suspending and froze a Blazor WebAssembly page. It also removes the
cases where work was in flight and the object did not know: a write through a MudNeatoo input,
`RunRules(propertyName)`, a `RunRules()` that was not awaited, a lazy load.

Most applications rebuild and change nothing. The breaks are in members documented as framework
use, and in code that implements Neatoo's services or properties itself.

## What's fixed

### `WaitForTasks()` no longer freezes a single-threaded page

Before 0.37.0 async work was recorded twice: as tasks on the entity, and as busy flags on each
property. `WaitForTasks()` awaited the tasks and then polled the flags. A property that was busy
with work the entity had no task for gave the loop nothing to await, so it never suspended. On one
thread, which is Blazor WebAssembly, the page froze with no exception.

The flags are gone. A property holds its work in flight as tasks and reports each one to its
entity, and `WaitForTasks()` is the entity's running tasks and nothing else.

Both paths named as still open in the [0.36.1 notes](v0.36.1.md) are closed:

- `RunRules(propertyName)` followed by `WaitForTasks()`.
- A write through a MudNeatoo input, followed by `WaitForTasks()` on the entity while an async rule
  from that write is still running. This path is now measured: three component tests that render a
  `MudNeatooTextField` hang the test host on 0.36.1 and pass on 0.37.0.

### Every write is tracked, whoever makes it

The object that owns the work registers it. Before, the code that started a write registered it,
so a write was tracked or not depending on how it was made. These are now all waited for by
`WaitForTasks()` on the object and on every parent up to the root:

| Work | Before 0.37.0 | 0.37.0 |
|---|---|---|
| A property setter, `Set{Name}` | Tracked | Tracked |
| `IValidateProperty.SetValue` (every MudNeatoo input) | Not tracked | Tracked |
| `RunRules(propertyName)`, not awaited | Not tracked | Tracked |
| `RunRules()`, not awaited | Not tracked | Tracked |
| A lazy load in flight | Reached through the property only | Tracked |
| A write on an item of a list | Depended on how it was made | Tracked |

### `WaitForTasks(token)` and `Save(token)` wait for the same work

`WaitForTasks(token)` skipped property-level work that `WaitForTasks()` covered, so `Save(token)`
could route to `[Insert]` or `[Update]` while a rule was still running. It is now the same wait
with cancellation. Cancelling it stops the wait; the rules run to completion.

### When `WaitForTasks()` completes, nothing is busy

`IsBusy` on an object is "its running tasks are running", so the wait completing and `IsBusy`
going false are one event. The `IsBusy` notification for going idle is raised before the wait
completes, so code that awaits `WaitForTasks()` and then looks at what its `PropertyChanged`
handler recorded sees the idle notification
([#129](https://github.com/NeatooDotNet/Neatoo/issues/129)).

Three ways `IsBusy` could be wrong are gone with the flags:

- An entity could read busy for good after an async rule threw.
- With two writes in flight on one property, the first to finish marked the property idle.
- A property holding a child object ignored its own work in flight.

### A rule that throws surfaces once, and the object recovers

A rule that throws is still an application failure, not a validation result: the awaiter of the
write gets the exception, and the trigger property keeps its message, so the object is invalid and
unsavable until the rule runs clean.

What changed is what happens next. Before, the entity's tracker stayed faulted: every later
`WaitForTasks()` threw the old exception again, and later work went untracked. Now the fault is
reported once, in an `AggregateException`: by the waits that were waiting on the faulted work, or,
when none was, by the next `WaitForTasks()`. After that the object tracks and waits for later work
as before.

### Raising `NeatooPropertyChanged` awaits every subscriber

`NeatooPropertyChanged` handlers return tasks. With more than one subscriber, only the last
handler's task was awaited, so a rule cascade could go unawaited because something else had also
subscribed to the same property or object. Every subscriber's task is now awaited.

### A busy item added to a `ValidateListBase` is waited for

An entity list refuses an item that is busy. A `ValidateListBase` accepts one, and the work that
item started before it had a parent was unknown to the list's owner. The new parent now waits for
it.

## What's new

### The task tracker comes through DI

The tracker is `IAsyncTasks`, supplied through the services an object already takes
(`IValidateBaseServices<T>.CreateAsyncTasks()`) and, for a property, through `IFactory`. Register
`IAsyncTasks` or the `CreateAsyncTasks` delegate after `AddNeatooServices` to replace it.

## Not in this release

- **A second `Save()` while one is in flight** still sends a second `[Insert]`
  ([#103](https://github.com/NeatooDotNet/Neatoo/issues/103)). A save in flight does not make the
  entity busy. Keep the guard in the page or ViewModel that ignores a second click.
- **Threads.** A Neatoo object graph is used from one thread at a time, as a UI application uses
  it. Nothing here changes that ([#131](https://github.com/NeatooDotNet/Neatoo/issues/131)).

## Migration

Rebuild. The source generator's output changed: a generated setter and `Set{Name}` no longer
register their work, because the object does. Generated files that are checked in will change.

### Compile breaks

Each of these is a member documented as framework use, or a type under `Neatoo.Internal`.

| Change | Who is affected | What to do |
|---|---|---|
| `IValidateProperty.AddMarkedBusy` and `RemoveMarkedBusy` are removed, with `IsSelfBusy` and `IsMarkedBusy` on `ValidateProperty` | Code that marked a property busy by hand | Remove the calls. A property is busy while it has a task in flight. A custom property class tracks its own work with the protected `TrackTask(task)` |
| `AddChildTask` is off `IValidateBase`, and `protected virtual` on `ValidateBase` | Code that registered a task with an entity; an override declared `public` | Remove the call: the object registers the work it starts. Change an override to `protected` |
| `IValidateBaseServices<T>` gains `CreateAsyncTasks()` | A class that implements or wraps the services | Forward it to the wrapped services |
| `IFactory` gains `CreateAsyncTasks()`; `DefaultFactory` takes a `CreateAsyncTasks` and is registered transient, not singleton | A custom `IFactory` | Implement the member. A registration that replaces `IFactory` should be transient too, because the tracker factory resolves from the caller's scope |
| `ValidateBase.RunningTasks` is typed `IAsyncTasks`; `AsyncTasks.AddTask(Task, bool)` is `AddTask(Task)` | A subclass that used `RunningTasks` directly | Drop the second argument |
| `ValidatePropertyManager.IsBusy` has no setter | A custom property manager that set it | Remove the assignment: it is read from the properties |

### Behavior changes

**1. `WaitForTasks()` after a faulted rule throws once, not every time.** Code that caught the
exception from every wait after a failure now catches it once. Code that treated an entity as dead
after a rule threw can keep using it.

**2. An awaited `RunRules()` or `RunRules(propertyName)` that throws is also reported by the next
`WaitForTasks()`.** The awaiter gets the rule's exception, as before. The rule run is now also the
object's registered work, so the next `WaitForTasks()` reports the same exception once, as it
already did for an awaited `Set{Name}`.

**3. A UI edit whose rule throws reaches `WaitForTasks()` on the entity.** A write through a
MudNeatoo input was not tracked, so its rule's exception never reached the entity's wait. It does
now, once. A save handler that awaits `WaitForTasks()` sees it.

**4. A `NeatooPropertyChanged` handler's task is part of the write.** The write's task does not
complete, and the object stays busy, until every handler's task has. Two consequences:

- A handler must not await `WaitForTasks()`, `RunRules(RunRulesFlag)` or `Save(token)` on its own
  object or a parent. It would wait for itself. Before, such a handler escaped only when a later
  subscriber's task replaced its own. `RunRules(propertyName)` does not wait on the object's
  running tasks, so a handler may still await it.
- A slow handler now delays the write it handles and keeps the object busy for as long as it runs.

**5. An object's `IsBusy` is its running tasks alone.** A custom property class that reports
`IsBusy` without tracking a task no longer makes its object busy or holds its wait open. Track the
work with `TrackTask(task)`.

**6. `Save(token)` waits for work it used to skip.** It may now wait, or be cancelled, where it
went straight to persistence with a rule still running.

**7. A list's `IsBusy` is read from its items.** It was a cached flag. Reading it costs a walk of
the items: about 13 µs for 1,000 items and 176 µs for 20,000, measured in Release. The list does
not walk its items on the notifications it handles, so the cost of adding to and editing a large
list is unchanged. Avoid reading a large list's `IsBusy` in a tight loop.

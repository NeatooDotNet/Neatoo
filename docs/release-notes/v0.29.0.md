# v0.29.0

**Release date:** TBD
**Breaking changes:** Yes

## Summary

`IsNew` is no longer part of `IsModified`. A freshly created entity is now **savable but not modified**, which lets unsaved-changes guards bound to `IsModified` stay quiet until the user actually edits something — including immediately after a save re-derives an object.

This release also fixes several defects in list and factory-lifecycle state that the change depended on, and corrects the reference documentation, which had been teaching a child-persistence pattern the framework does not implement.

## Why

`IsModified` was being asked two different questions and could only answer one:

| Property | Question | Drives |
|---|---|---|
| `IsModified` | Would discarding this lose work? | Unsaved-changes prompts, navigation guards |
| `IsNew` | Does persistence not know this object yet? | Insert-vs-update routing |

For a fetched-then-edited entity the answers coincide. For a **created** entity they diverge: it needs persisting, but holds no user work. The old derivation forced both answers to `true` structurally — the `IsNew=true / IsModified=false` state was *unreachable*, not merely unset. Applications compensated per-callsite with hand-splits like `IsNew ? HasData : IsModified`.

Savability was the reason the weld existed: `IsSavable` rode on `IsModified`, so a created object had to claim dirtiness to stay savable. Admitting `IsNew` into `IsSavable` removes that reason.

## What's new

### Core semantics

```csharp
IsModified  => PropertyManager.IsModified || IsDeleted || IsSelfModified;   // IsNew term removed
IsSavable   => (IsModified || IsNew) && IsValid && !IsBusy && !IsChild;
// Save() NotModified guard now: !(IsModified || IsNew)
```

After `[Create]`: `IsNew=true`, `IsModified=false`, `IsSavable=true` — including aggregates whose factory populated their children.

### Opt-in dirty create

A `[Create]` whose result *is* the user's work (a "New Invoice" button, rather than a derived default) declares it with the existing `MarkModified()`:

```csharp
[Create]
public void Create() { MarkModified(); }
```

This uses no new API and survives a remote round trip (`IsMarkedModified` already serializes).

> **Common mistake:** calling `MarkModified()` in a `[Create]` so the entity can be saved. New entities are already savable. Using it that way re-welds the two meanings and brings back the cry-wolf guards.

### Attach-marking

Modification state — never `IsNew` — is what aggregates up an object graph, so attaching a child to a **live** parent now marks the child modified:

- adding an item to a list that is not paused (the `!IsNew` exemption is gone), and
- assigning a **new** child entity to a parent property.

Baseline population is unaffected: children loaded or created inside a paused factory operation are not marked, which is what keeps rich `[Create]` and `[Fetch]` clean. Assigning an already-persisted, unmodified child still does not dirty the parent, and list-valued properties need no mark (list state aggregates from its children).

### Fixes included

- **Lists reported the state of an empty list after a factory operation.** `FactoryComplete` resumed without recalculating cached meta state, so a list populated by its own `[Fetch]` could report stale `IsValid`/`IsBusy`.
- **Children loaded by a list `[Fetch]` were not marked as children.** `IsChild` stayed false and `ContainingList` null, so `child.Delete()` silently bypassed list routing and the row was never deleted at save. (`ContainingList` cannot be serialized; the paused add path is what re-establishes it on the client.)
- **A list going clean never announced it.** `EntityListBase.RemoveItem` updated its cache after the base class had already run its notification check, so the parent's cached `IsModified` stayed true forever. Symptom: add a child, remove it, and the aggregate still claimed unsaved changes with nothing to save.
- **Remove-then-re-add of a fetched child** left it in the DeletedList *and* the collection, so the next save would both update and delete it.
- **The cross-aggregate boundary error named both aggregates by type**, so the common case read `belongs to aggregate 'Order', but this list belongs to aggregate 'Order'`. It now distinguishes same-type aggregates by instance and names the supported alternative.

### Documentation

`Design.Domain` — the authoritative API reference — taught a child-persistence pattern the framework does not implement: it claimed a parent's `FactoryComplete` cascades to children (it does not; lifecycle hooks fire per factory target), and its aggregates loaded children with `Create()` + `LoadValue` so fetched children came back `IsNew=true` and would be re-inserted on the next save. The `OrderAggregate` and `Entities` aggregates now demonstrate the canonical shape: list `[Fetch]` → item `[Fetch]`, and child persistence routed through per-item factory saves. The Save-routing documentation was also corrected against the emitted factory code (routing checks `IsDeleted`, then `IsNew`, and never consults `IsModified`).

## Migration guide

**1. `if (entity.IsModified) Save()` will silently skip fresh creates.**

```csharp
// Before — worked only because IsNew implied IsModified
if (order.IsModified) await order.Save();

// After
if (order.IsSavable) await order.Save();
```

**2. Guards that should warn on *any* new object need to say so.** The new default is usually what you want; if you deliberately want a prompt on an untouched new object, ask for it:

```csharp
if (order.IsNew || order.IsModified) { /* warn */ }
```

**3. Per-callsite hand-splits can be deleted.** Patterns like `a.IsNew ? a.HasData : a.IsModified` were working around the weld and are now redundant — `a.IsModified` says it directly.

**4. Tests asserting `IsModified == true` after `Create()` will fail** and should assert `IsNew` and/or `IsSavable` instead. If a particular create really is user work, add `MarkModified()` to the factory method rather than changing the assertion.

**5. Observable shifts on attach.** Items attached to a live list now report `IsMarkedModified`/`IsSelfModified` as true (previously new items were dirty via the weld instead). Assigning a new child entity to a parent property still dirties the parent, by the new mechanism rather than the old one.

**Not affected:** factory save routing (it dispatches on `IsDeleted`/`IsNew` and never read `IsModified`), `IsDeleted` semantics, serialization contracts, and MudNeatoo (which consults none of these flags).

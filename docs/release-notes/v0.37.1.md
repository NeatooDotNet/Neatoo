# Neatoo 0.37.1

**Release date:** Not released
**Breaking changes:** No

## Summary

One fix. A second `Save()` on an aggregate root while the first was still in flight sent a second
`[Insert]`. While a save is in flight the object is now not savable, says so, and refuses a second
`Save()`.

## What's fixed

### A double-click on Save sent two inserts

`entity.Save()` checked `IsSavable` and handed the object to its factory without changing anything on
it, so during the call the object still read savable. A second click on a Save button bound to
`IsSavable` therefore saved it again
([#103](https://github.com/NeatooDotNet/Neatoo/issues/103)). Measured by a consuming application on
0.36.1: through HTTP against PostgreSQL one save failed on the primary key, and with a store that has
no key the aggregate was stored twice.

From 0.37.1, while `entity.Save()` runs:

- `IsSavable` is false, and the object raises `PropertyChanged("IsSavable")` when the save starts and
  again when it returns. A Save button bound to it disables for the length of the save.
- A second `Save()` or `Save(token)` on the same object throws `SaveOperationException` with the new
  reason `SaveFailureReason.SaveInProgress`, and sends nothing.
- `IsBusy` and `WaitForTasks()` do not change. A save in flight is its own state, not busy (D39 in
  `docs/VisionAlignment.md`): a local save completes on the same instance while `Save()` is still
  running, and an operation body may await the object it is saving.

When the save returns, whatever the outcome, the object is savable again if it still has something to
save:

- **After a remote save** that is the instance that was sent. It is stale; reassign the instance
  `Save()` returns, as before (D41).
- **After a save that failed** it is what lets the user fix the cause and save again.
- **After a local save** the instance was saved and has nothing left to save.

Not covered: a save started by calling the factory's `Save(target)` directly, which does not come
through `entity.Save()`.

## What to change

Nothing is required. A save handler or ViewModel that keeps its own flag to ignore a second click can
drop it: the button bound to `IsSavable` disables, and a second call is refused.

Code that switches over `SaveFailureReason` without a default branch has one more value to handle.

## Tests

`SaveInFlightTests` (new): eleven tests over a remote and a local aggregate with an async `[Insert]`,
covering the refused second save with and without a token, the `IsSavable` value and its
announcements, `IsBusy` and `WaitForTasks()` during a save, the sent instance after a remote save, and
a failed save tried again. No existing test changed.

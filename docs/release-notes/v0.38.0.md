# Neatoo 0.38.0

**Release date:** 2026-11-26
**Breaking changes:** Yes — see [Migration](#migration).

## Summary

Neatoo's generated code and the library itself now compile clean with nullable reference types on.
An application can keep nullable warnings as errors in its domain project without suppressing
CS8603.

One signature changed to tell the truth: `Save()` returns `Task<IEntityBase?>`. It always could
return `null`; the type now says so. That is the breaking change.

## What's fixed

### A non-nullable reference partial property raised CS8603 in generated code

A partial property declared with a non-nullable reference type got a generated getter that returned
`IValidateProperty<T>.Value`, which is `T?`:

- `public partial string Name { get; set; }`
- `public partial IReadOnlyList<Guid> BoxIds { get; private set; }`

In a project with nullable enabled, each such property raised CS8603 (possible null reference
return) inside the generated file, where the application cannot fix it. Applications that treat
warnings as errors either suppressed CS8603 for the whole domain project, which also hid it in their
own code, or declared every reference partial nullable.

The generated getter now returns `Value!`. Nothing changes at runtime: a property that has not been
set still reads `null`, as before. A caller sees the same declared type it always saw; the compiler
checks callers against the declaration, not the getter body.

Not changed: nothing tells you at compile time that a non-nullable reference partial is `null` until
a `[Create]` or `[Fetch]` assigns it. A plain auto-property gets CS8618 for that; a partial property
does not.

### Neatoo no longer suppresses nullable warnings for itself

`Directory.Build.props` suppressed 15 nullable warnings for the whole repository, so nothing in
Neatoo's own build could show the problem above. All 15 are removed. The library had 44 places that
then warned; each is fixed. The ones with an effect you can see:

- **Malformed JSON.** `NeatooBaseJsonTypeConverter` and `NeatooListBaseJsonTypeConverter` failed
  with a null-reference or argument-null exception on JSON with a missing `$type`, a type name the
  application does not know, or fields out of order. They now throw `JsonException` with a message
  that says what is wrong. Well-formed JSON reads as before.
- **`AddTransientSelf` and `AddScopedSelf`** resolve the interface registration with
  `GetRequiredService`. If that registration has been removed, resolving the concrete type throws
  instead of returning `null`.
- **`ValidateBaseServices<T>(IPropertyInfoList<T>, RuleManagerFactory<T>)`** left
  `ValidatePropertyManager` unset. It now creates the default one, as the parameterless constructor
  does.

Test projects that still suppress a nullable warning say so in their own project file.

## Migration

### `Save()` returns `Task<IEntityBase?>`

`IEntityRoot.Save()` and `EntityBase<T>.Save()`, with and without a token, were declared
`Task<IEntityBase>`. They return what the generated factory returns, and the factory returns no
instance for an entity that is both new and deleted: there is nothing to persist, so no operation
runs. `Save()` returned `null` in that case under a declaration that said it could not. The
declaration is now `Task<IEntityBase?>` (ruling D42 in `docs/VisionAlignment.md`).

A factory with authorization (`[AuthorizeFactory]`) does not return `null` in that case today. It
throws `NotAuthorizedException`, although no authorization check ran. That is a RemoteFactory bug,
tracked as NeatooDotNet/DTZero#11, and this release does not change it.

Nothing changes at runtime. With nullable enabled, a call site that casts the result to a
non-nullable type now warns (CS8600):

```
order = (IOrder)await order.Save();   // CS8600 from 0.38.0
```

Choose by what holds the result:

- **A nullable holder**, such as a ViewModel property declared `IOrder?`: cast to the nullable type,
  `Order = (IOrder?)await Order.Save();`.
- **A non-nullable local, for an entity you did not delete:** `order = (IOrder)(await order.Save())!;`.
  The parentheses matter: `await order.Save()!` applies the `!` to the task, not to its result.
- **Where no instance is an error:** `(IOrder?)await order.Save() ?? throw ...`.

The save handlers in `Design.App/ViewModels/` and the job in `Design.Domain/Jobs/SubmitDraftOrders.cs`
show the first and third forms.

### Smaller signature changes

- `ValidatePropertyManager<P>`'s indexer returns `P`, not `P?`. It always threw
  `PropertyMissingException` for an unknown name and never returned `null`; the interface already
  said `P`.
- `RuleProxy.Target` is `IValidateBase?`. Nothing sets it on construction.
- `NeatooBaseJsonTypeConverter<T>.Read` returns `T?`, as its base class declares.

### Applications that worked around CS8603

After upgrading, remove a `<NoWarn>` for CS8603 that was added for the generated getters, and
rebuild. Reference partials that were declared nullable only to avoid the warning can be declared
non-nullable again where that is what they are.

## Tests

- `NullableGetterGenerationTests` (new, 2 tests): compiles generated code with nullable enabled and
  expects no warnings, for non-nullable reference partials and, as a control, for nullable and
  value-type partials. On the unchanged generator the first failed with four CS8603.
- `SaveTests.Save_WhenNewAndDeleted_RunsNoOperationAndReturnsNull` (new): pins the case that makes
  `Save()` nullable.
- `PartialPropertyGenerationTests`: two assertions matched the generated text `Property.Value;` and
  now match `Property.Value!;`. Both still claim that the getter reads `Value`.
- `EntityRootInterfaceTests.RootInterface_ExposessSave` asserts the new `Save()` signature
  (`Task<IEntityBase?>`), per D42.
- `Design.Tests`: 19 call sites use `(IOrder)(await order.Save())!`, and two other lines gained a
  `!`. Five event handlers in `Neatoo.UnitTest` take `object? sender`. No other test's claim changed.

# Neatoo 0.36.1

**Release date:** 2026-11-24
**Breaking changes:** No

## Summary

One fix. An entity or list that came through the serializer handled each property change twice at
every level of the graph. It now handles it once, as an object built in the same container does.

## What's fixed

### A deserialized entity or list handled each property change twice per level

Everything a client receives from a `[Remote]` operation is built by the serializer, so this applied
to every fetched or saved aggregate on the client
([#140](https://github.com/NeatooDotNet/Neatoo/issues/140)).

One write to a property on a deserialized object ran each triggered rule twice and raised
`PropertyChanged` twice. The factor doubled at each deserialized level above the write:

| One write to a child's property | Built in this container | Deserialized, before 0.36.1 | 0.36.1 |
|---|---|---|---|
| The child's rule | 1 | 2 | 1 |
| The list's `HandleNeatooPropertyChanged` | 1 | 4 | 1 |
| A root rule on `t => t.Items![0].X` | 1 | 8 | 1 |

A second round trip did not add to it, because each deserialization builds new instances.

The cause was three second subscriptions made during deserialization: the entity to its property
manager, the list to each item, and the property manager to any property that is not in the JSON
(the lazy-load ones). A subscription is now made where an object is attached and nowhere else.

What this changed in practice:

- A rule that calls the server sent 2, 4 or 8 requests for one write.
- Only the last of those runs was tracked. The others still marked their trigger property busy, and
  when one of them outlived the tracked run, `WaitForTasks()` could reach the loop described below.

The defect is in every earlier version.

## Known issue, not fixed here

`WaitForTasks()` can loop without ever suspending while a property is busy with a rule the entity is
not tracking ([#141](https://github.com/NeatooDotNet/Neatoo/issues/141)). On one thread, which is
Blazor WebAssembly, that freezes the page with no exception. It has been reachable since 10.10.0.

After 0.36.1 a run dropped by the double subscription no longer reaches it. Two paths still do:

- `RunRules(propertyName)` followed by `WaitForTasks()` before the first call has been awaited to
  its end. Await `RunRules` first.
- A write made with `IValidateProperty.SetValue`, which every MudNeatoo input uses, followed by
  `WaitForTasks()` on the entity while an async rule from that write is still running. This one is
  read from the code and has not been measured.

The fix is a change to how Neatoo tracks async work, planned for a later release.

## Migration

None. Applications change nothing.
